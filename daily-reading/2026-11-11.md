# November 11, 2026: Make the sorting loop measurable

**Read time:** about five minutes  
**Sources checked:** 2026-11-11 (UTC)  
**Project snapshot:** [`48c19d6`](https://github.com/LiamHoweth/RAFTEL/commit/48c19d6144051ef66d26d465f3b6f398580e1a90)

## If you read one thing

Read the [LeRobot v0.7.0 release](https://huggingface.co/blog/lerobot/lerobot-release-v070), especially hardware, recording, and evaluation. For the first sorting arm, a repeatable loop of **record → test → inspect failures → improve** is more useful than immediately chasing general-purpose humanoid autonomy.

That is a recommendation for the project, not a decision to adopt LeRobot.

## Where RAFTEL is today

At the snapshot above, the entire repository contained only [README.md](https://github.com/LiamHoweth/RAFTEL/blob/48c19d6144051ef66d26d465f3b6f398580e1a90/README.md), describing RAFTEL as “humanoid.” There were no code, hardware specifications, tests, project instructions, or open issues/PRs to assess.

The owner's stated first milestone is a full-range arm on a clamped stand that sorts objects into boxes, with a later move to a mobile home assistant. This first brief uses that plan; it does **not** claim the design is already implemented. The expected `nextSteps.md` and incoming project files should drive subsequent recommendations.

## Recent news worth reading

### 1. LeRobot v0.7.0 adds live language interaction and remote inference

**Published:** November 5, 2026. **Priority:** read now.

The maintainers describe interactive policy rollouts, remote GPU policy serving, additional robot support, and expanded data/training workflows. Language-based questioning and autonomous subtask selection require a suitable text-generating policy or an external planner. [Original release](https://huggingface.co/blog/lerobot/lerobot-release-v070).

**Why it matters:** it offers an existing path from arm control and recorded demonstrations toward learned sorting. Before building a custom data pipeline, compare the selected hardware with supported interfaces. The [SO-101 documentation](https://huggingface.co/docs/lerobot/so101) illustrates setup and calibration, but RAFTEL has not selected that arm.

**Takeaway:** evaluate recording and repeatable testing first. Defer open-ended planner-driven motion until bounded behavior and independent stop mechanisms are established. Verify version-specific compatibility before adopting anything.

### 2. NVIDIA introduces GR00T 2 and Isaac Lab 3.0 at CoRL

**Published:** November 9, 2026. **Priority:** scan now; evaluate later.

NVIDIA's announcement emphasizes dexterous manipulation, simulation, and transfer across robot bodies. It reports GR00T 2 completing 40 of 50 evaluated tasks **at least once** without task-specific demonstrations. That is not the same as an 80% per-trial success rate. [Original announcement](https://blogs.nvidia.com/blog/robotics-simulation-advancements-corl/).

**Why it matters:** sorting eventually needs more than a convincing demo. The useful lesson is to evaluate across object poses, clutter, and failures. The source also describes arm-based manipulation, so the relevance is not limited to humanoids.

**Takeaway:** consider simulation after the arm's geometry and task are defined. These are vendor-reported results, not evidence that the model is compatible with RAFTEL or that adopting this compute stack is necessary.

## What other companies are doing

### Physical Intelligence: hosted fine-tuning and inference

**Published:** October 13, 2026. **Label:** recent background, not today's news.

The Pi API beta lets users upload demonstrations, fine-tune models, and run hosted inference. Its own write-up describes an iteration loop guided by robot failures and notes connectivity challenges in some deployments. [Original announcement](https://www.pi.website/blog/api-beta).

**RAFTEL implication:** build clean recordings and an evaluation set so that local and hosted approaches can eventually be compared. Keep low-level limits and stop behavior independent of a remote service. No account, upload, or service adoption is implied by this reading recommendation.

### Figure: test beyond the room used for training

**Published:** September 17, 2026. **Label:** longer-term background.

Figure reports evaluating Helix 2.5 on tidying, towel folding, and bed making across 30 unseen homes. It reports 56% zero-shot whole-task success with Index pretraining versus 9% without. “Zero-shot” refers to the evaluation homes and objects; the behaviors still used task-specific training elsewhere. These are company-reported results. [Technical write-up](https://www.figure.ai/news/helix-2-5-zero-shot-30-home-generalization).

**RAFTEL implication:** for the later home-assistant goal, generalization is a separate test. Even the stationary arm can start with objects and layouts held out from demonstrations. This is useful evaluation design, not a reason to add locomotion to milestone one.

## A practical next step

**Suggested experiment, once the hardware is defined:** write down one small sorting task and its success criteria before collecting demonstrations.

- Fix the initial object set, target boxes, workspace, and starting conditions.
- Record correct-box placements, dropped objects, wrong-box placements, cycle time, and human interventions. A successful grasp alone is not a successful sort.
- Reserve a separate set of object positions and, later, unfamiliar objects for evaluation.
- Record camera placement, calibration, software version, and control settings alongside each run.
- Start with a secured mount, manufacturer-appropriate limits, a clear workspace, and an independently available stop. A research model is not a safety system.

These are proposed evaluation criteria, not completed work or a replacement for `nextSteps.md`.

## What remains unknown

Arm geometry, actuators, gripper, sensors, compute, budget, control stack, and the initial object set are not yet in this repository snapshot. Until they are, hardware purchases, model compatibility, and implementation recommendations would be premature.
